# A newly plowed meadow shows on the minimap's field picture only much later (MapOverlayGenerator)

**Status:** cause read in the game scripts; mitigation in this mod (`scripts/FieldsOverlay.lua`), 12 offline checks (a fake generator and fake field work); **confirmed in the running game
(2026-10-30): a meadow plowed shows on the minimap's picture while plowing.** Measured in the game: a generation of the fields picture takes about **210 ms** (longest 245 ms), so a cycle
of the game's own timing is about 5.2 s and nearly all of it is the 5 s wait, not the engine.
**Game version:** FS25 as installed 2026-10-30, scripts as read from the game archive and the decompiled `MapOverlayGenerator`, `IngameMap`, `FSDensityMapUtil`.

## Symptom

Plow (or cultivate) a meadow: it is a field in the game's data at once (the ground type is set), but the minimap's field picture (the green areas) shows it only a long time later.

## Cause

* `IngameMap:drawFields` draws `MapOverlayGenerator:getFieldsOverlay()`: a **density map visualization overlay** of the ground type map (512 x 512), generated by the engine in the background
  (`generateDensityMapVisualizationOverlay`), the whole map at once.
* `MapOverlayGenerator:update` (called every frame from `FSBaseMission:update`) starts a generation when `fieldsRefreshTimer < g_time`; the callback that comes when the engine has finished sets
  `fieldsRefreshTimer = g_time + FIELD_REFRESH_INTERVAL` (5000 ms) and shows the new picture. **Nothing starts a generation because the ground changed.**
* `FSDensityMapUtil.updatePlowArea` (and `updateCultivatorArea`, `updateDiscHarrowArea`, `updatePlowShareArea`) set the ground type with `createField` (default `true`) and return the area they
  changed, so the data is right at once; only the picture lags: a patch plowed just after a generation began is not in it, and has to wait for the rest of that generation, the 5 s, and one whole
  generation more (measured in the game: a generation takes about 210 ms, so one cycle is about 5.2 s and a new field shows after one to two cycles, 5 to 10 s, instead of about 2 to 4 s with this mod).

## Suggested change for the game

The functions that change a field's ground type already know when they have changed something (their return value). Let them tell the overlay generator (`g_currentMission.mapOverlayGenerator`),
which then starts its next generation as soon as the running one is finished (not 5 s later). If the engine can limit a generation to a region, only the changed region needs to be redone; the
Lua API used (`generateDensityMapVisualizationOverlay(handle)`) has no region.

## What this mod does

* After every update of the generator it sees a generation start and finish (`fieldsOverlayUpdating`) and times it.
* The four field work functions are wrapped: when one returns a changed area above zero, a change is noted.
* A noted change brings the generator's timer forward: the next generation starts `MIN_GAP_MS` (2000) after the last one finished instead of 5000 (a change noted while a generation runs
  is picked up when it finishes: that generation began before the change). While there is no field work nothing is noted and the game's own timer runs as before; the engine is never asked
  for two generations at once.
* Once a minute the log says how many generations there were, how long each took (average and longest) and how often one was brought forward.

## The real cause of a picture that stops updating: two generations at once (found in the log 2026-10-30)

`MapOverlayGenerator` builds every overlay (fields, crops, growth, soil, farmlands) with **one** `currentOverlayHandle` and **one** `overlayFinishedCallback`. A second generation started while one
is running (the big map starts its own the moment it opens; the fields one starts on its 5 s timer) overwrites the first one's callback, which is then never called. For the fields overlay that
leaves `fieldsOverlayUpdating` true for good: the picture is never regenerated again until the game is restarted. In the log: `big map was open ... the picture was 162.3 s old when it opened` and
no more `fields overlay: N generation(s) in the last minute` lines (they only print when there was a generation). This is the likely cause of "the big map is outdated" and it is a game bug
(it needs only the two overlays to start within one generation, about 0.2-0.6 s, of each other).

This mod: a generation requested while one runs **waits** (`rfWaiting`, started from the wrapped `checkOverlayFinished` when the running one is done; a later request of the same kind replaces
a waiting one), and a fields generation that has been running for `STUCK_MS` (10 s) with nothing in flight is declared lost: the flag is reset and the log says
`a generation of the fields picture never finished`. Offline: 9 more checks. **Not confirmed in the game yet.**

## The big map (pause menu): first guess, refuted

(The pause is NOT the cause: the log shows the game updating the generator in all but one frame of the menu.) What follows was the first guess and is kept for the record; the open / frame hooks are
harmless but the queue above is what matters.

The big map is the same `IngameMap` class in its fullscreen layout (`InGameMenuMapFrame.ingameMap`), so it draws the same picture (`getFieldsOverlay`). But `MapOverlayGenerator:update` is
called from `FSBaseMission:update`, and the pause menu stops the game: **while the menu is open the picture is never regenerated**, so the big map shows the ground as it was when the menu
was opened, which is up to a cycle (5 s and more) behind, and a patch plowed in the last seconds not at all. (Reported 2026-10-30: the minimap was current after the fix above, the big map not.)

This mod: `InGameMenuMapFrame.onFrameOpen` sets the generator's timer back so a generation starts at once (if one is running, a follow-up is asked for), and the frame's own `update`
calls the generator when the game has not updated it since the previous menu frame. On closing, the log says how many frames the menu had, in how many the game itself updated the generator
(this tells whether the pause is the cause: 0 means yes), and how old the picture was when the menu opened. **Not confirmed in the game yet.**
